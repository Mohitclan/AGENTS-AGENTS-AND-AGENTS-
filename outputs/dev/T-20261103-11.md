## The bug

`node scripts/leads.mjs suppress https://www.linkedin.com/in/asha "<reason>"` printed `Suppressed linkedin.com.` and stored `{"value":"linkedin.com"}`. The same happened for X (`x.com`).

- On `main`: that entry matches no lead, so the person's opt-out is not enforced. They can still be drafted for and emailed. This breaks hard rule 7, and was already true before 09a.
- With the 09a gate (`92931ef`): the same entry stops every lead whose contact is on that host (in the real pipeline, Cool Analytics on LinkedIn and SpaceWise on an `x.com` URL).
- Three matchers disagreed about what an entry covers, so the same list gave different answers depending on the command.

## Root cause

`scripts/leads.mjs` at `92931ef`:
- Line 264, in `suppress`: `.replace(/\/.*$/, '')` removes everything after the host. A profile on a shared site cannot be told apart from the site.
- Line 257, `suppressedBy` (import, `set-status`, the at-once disqualify in `suppress`): exact lead domain or exact contact address only.
- Line 288, `suppressionHit` (gate only): also parent domains and the contact's host. This is what turned the bare `linkedin.com` entry into a site-wide block.
- `scripts/send-email.mjs` line 82, `isSuppressed`: exact address or that address's exact domain.

## The fix

One matcher, `suppressionMatch(list, { contact, website, domain })` in `scripts/_shared.mjs`. I could not put it in `leads.mjs` and import it from `send-email.mjs`: `leads.mjs` runs its command line at load (`switch (command)` at the bottom, no `isMain` guard), so importing it would exit with a usage error. The brief allowed `_shared.mjs` for this case.

An entry is one of:
- an email address: that address only (a leading `mailto:` is stripped);
- a company domain: the domain, its subdomains and addresses on them (label boundary, so `notexample.com` is not covered);
- a profile URL: that page and the pages below it, on a `/` boundary.

A shared host is never a company domain. `SHARED_HOSTS` (in `_shared.mjs`, the list is `PROFILE_PATH_HOSTS` plus `PROFILE_SUBDOMAIN_HOSTS`): linkedin.com, x.com, twitter.com, github.com, gitlab.com, medium.com, substack.com, facebook.com, instagram.com, youtube.com, producthunt.com, peerlist.io, wellfound.com, threads.net, bsky.app, dev.to, **linktr.ee, calendly.com, bento.me, about.me, read.cv (added in revision 1)**, and the subdomain hosts github.io, gitlab.io, vercel.app, netlify.app, pages.dev, hashnode.dev, notion.site, carrd.co, webflow.io, blogspot.com, wordpress.com (plus subdomains of medium.com and substack.com). I chose the extras beyond the seven the brief named; trim or extend the list in one place.

`suppress` (`classifySuppression`, which reads the value with one internal function, `readSuppression`):
- Email: stored lower-case; `mailto:` and any `?subject=` are stripped first.
- A page on a shared host: stored as a normalised URL, the `https` scheme + lower-case host (no `www.`, `m.`, `mobile.`; LinkedIn country sites collapse to `linkedin.com`; `twitter.com` becomes `x.com`) + lower-case path, with no fragment or trailing slash and no query, except that `facebook.com/profile.php?id=123` keeps its `id`. Example: `HTTPS://www.LinkedIn.com/in/Asha-A/?utm=x#top` is stored as `https://linkedin.com/in/asha-a`. `https://asha-page.github.io/` is stored as `https://asha-page.github.io`.
- A bare shared host (`linkedin.com`, `https://www.linkedin.com/`, `github.io`, ...): refused with exit 1: "linkedin.com is a shared site: suppressing it would cover everyone who has a page there. Give the person's profile URL instead, for example https://linkedin.com/in/<name>". The refusal happens before the lock and before any write.
- A shared-host path that is not one person is refused with "does not name one person. Give the person's profile URL instead": `linkedin.com/in` (LinkedIn needs two segments, `in/asha`, `company/acme`), `x.com/i`, `x.com/home`, `youtube.com/c`, `youtube.com/channel`, `youtube.com/watch?v=...`, `github.com/orgs`, `facebook.com/profile.php` with no `id`. With a name after them (`youtube.com/c/acme`, `github.com/orgs/acme`) they are accepted. **(Revision 1.)** Only a Facebook `profile.php` page is identified by a query; every other query is dropped.
- A free-mail domain (`PERSONAL_MAIL`, moved into `_shared.mjs` so the gate's personal-mail signal and `suppress` read one list): refused, in any case or as a URL, with "gmail.com is a personal mail service: suppressing it would cover every address there. Give the person's email address instead". `asha@gmail.com` is still accepted. **(Revision 1.)**
- A bare public suffix (`co.uk`, `com.au`, `co.in`, ... from a built-in list of about 50 common two-part suffixes; a single label such as `de` is not a web address at all): refused. `canonicalHost` no longer cuts a company host down to a suffix: `www.` is dropped only if what remains is not a suffix, and `m.`/`mobile.` only on a shared host. So `mobile.de` is stored as `mobile.de`, `m.me` as `m.me`, `www.com` as `www.com`. **(Revision 1.)** The suffix list is a judgement, not the full public-suffix list; an uncommon suffix such as `co.zw` is not recognised.
- Anything that is not an email, a profile URL or a domain: refused. **(Revision 1.)**
- Anything else: a domain, as before.

## Risks

- **Wider matching everywhere.** Import, `set-status` and `suppress` now use the gate's wider match. A company-domain opt-out for `example.com` now also disqualifies a lead whose contact is `x@mail.example.com`, or whose website is a subdomain. That is the point of an opt-out, but it can surprise someone.
- **A profile URL cannot block an email.** `https://linkedin.com/in/asha` stops a lead with that LinkedIn contact. If the same person also has an email contact, or is emailed by a different lead, that needs its own entry. `send-email.mjs` only sees an address, so a LinkedIn-only entry cannot stop an email to the same person. Record both where both exist.
- **Prefix matching.** A profile-URL entry covers the pages below it (`github.com/acme` covers `github.com/acme/repo`), on a `/` boundary only. The brief said "exact profile URL"; I chose boundary prefix so a profile's sub-pages (`/details/...`) cannot slip past. `asha-a` does not cover `asha-ab`. The coordinator accepted this; it is pinned by a test.
- **Lower-case paths.** The stored path is lower-case. LinkedIn, X and GitHub handles are case-insensitive, so this is right for them; on a host with case-sensitive paths it could match another page that differs only by case, which fails safe (over-blocks).
- **Shared-host list is a judgement.** A site not in `SHARED_HOSTS` is treated as a company domain, so `suppress somehost.example` would cover everyone on it. A new shared site (a new link-in-bio service) needs adding to the list. `suppress` still stores a page on an unlisted host as its bare domain without saying so.
- **Free-mail domains are refused** (revision 1), from the same `PERSONAL_MAIL` list as the gate. That list is short and fixed: a mail service not on it (a regional provider) is accepted as a company domain and would cover every address there. A hand-written `gmail.com` entry still blocks every Gmail address, including the internal demo inbox `shivamkgjj2005@gmail.com` (main memory, 2026-11-02), and `check` fails on it.
- **Legacy shared-host entries over-block until a person acts** (revision 1). While `linkedin.com` is in the file, every lead whose contact or website is on LinkedIn is a Stop, import and `set-status` refuse them, and `check` exits 1, which may fail a script that runs `check` as a gate. That is the intended fail-safe: the bare entry cannot be tied to one person, so it must not quietly stop protecting them. It ends when a person re-enters the people as profile URLs and removes the bare line.
- **The suffix list is partial** (revision 1), see the `suppress` section.
- **Subdomain-tenant sites** (`asha.github.io`) are stored as URL entries, not domain entries. An old-format `asha.github.io` domain entry still works (it is not bare), so no migration is needed there.
- **Warning goes to stderr** for `gate`; `check` fails. A script that reads only the exit code of `gate` will not see the warning.
- The dashboard flake (Revision 1, tests) could look like a regression from this change; it is not.
