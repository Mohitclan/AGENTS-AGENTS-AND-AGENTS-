# T-20261104-17: Projects panel in mission control (UI)

Built against the "Routes" and "UI" sections of `outputs/dev/T-20261104-16-projects-spec.md`. That spec file is not committed (it sits untracked in the main checkout), so I read it from there. No server file was touched.

## The change

A **Projects** panel at the top of the Overview page, above the task box. It uses the four routes in the spec: `GET /api/projects`, `POST /api/projects/upload`, `POST /api/projects/work`, `POST /api/projects/<slug>/confirm`. Posts go through the page's existing `api()` helper, which adds the `X-Team-Page: 1` header.

- **Upload.** An "Upload knowledge.md" button, or drop one file on the panel. The browser reads it with `File.text()` and posts `{filename, content}`. The server's message is shown in a status line.
- **Cards.** One per project: name, slug, status chip, version, last updated, website link, history count, and any queued or running task. They refresh on every state-stream tick (at most one fetch per 5 s) and every 15 s.
- **Chips.** `confirmed` shows "Ready". `proposed` shows "Waiting for your confirm", or "Being prepared" while a task is running. `pendingUpdate` shows "Update v<n> waiting". Each chip has words and a mark (check, !, ...), so none relies on colour.
- **Tick boxes and action bar.** Tick boxes on each card, a "Tick all" box, and the buttons Research, Find leads, Draft outreach and Demo pack. A button is greyed unless every ticked card has `canWork[action]`, and it is also greyed with more than 5 ticked. Greyed buttons use `aria-disabled`, not `disabled`, so the keyboard can still reach them. They carry a tooltip, and one visible line under the bar says why.
- **Work result.** The server's message, then "Queued" and "Refused" lists with each refusal's reason, until dismissed.
- **Confirm dialog.** "Review and confirm" (or "Review update v<n>") on cards that need it. It shows "Confirming makes these facts usable in customer-facing work.", a link to the sheet in the existing file viewer, a "Your name" field, and a field for `confirm <slug>`. The Confirm button turns on only for a non-empty name and an exact match of the phrase (spaces at the ends are trimmed, case must match). A server refusal shows in the dialog, which stays open.
- **Upload new version.** A button on each card that uses the same flow. The browser refuses the file when the form declares a different `slug:` than the card.

Where I went beyond or away from the spec (the coordinator can reverse any of these):
1. **"Being prepared" counts only conversion or update tasks** (`tasks[].action` is `convert` or `update`). Work tasks and `other` tasks (a person's own task that names the project) don't hide the confirm button. (Corrected in revision 1; the first version also counted `other`.)
2. **A pending update's confirm button is hidden while a conversion task for it is still queued or running.** The server confirms the newest proposal, and a review revision could rewrite it after the click.
3. **Client-side checks mirror the server's:** .md name, 300 KB, text starts with `---`, and the slug match above. The server still decides.
4. **After a new upload the panel says the card appears once the team has written the draft sheet.** This follows from the spec's list route reading `knowledge/products/*.md`, so a new upload has no card until the sheet exists.
5. **A "Tick all" box** (not in the spec) so the 5-project limit can be reached and shown.

```
Confirm dialog (focus starts in "Your name"; Tab stays inside; Esc or Cancel closes):
  Confirm the facts for Acme CRM
  Confirming makes these facts usable in customer-facing work. Read the sheet first.
  Open acme-crm.md to review   knowledge/products/acme-crm.md
  Your name      [______________]
  Type confirm acme-crm to confirm   [______________]
  The Confirm button turns on when your name is filled in and the words match exactly. ...
  (error from the server appears here, role=alert)
                                              [Cancel] [Confirm]   <- Confirm off until both match
```

Other states: projects not loaded (the server has no route yet) show "Projects could not be loaded: Error 404 [Try again]". An empty list shows "No projects yet. Upload a knowledge.md to start one." A drag over the panel gives it a blue outline.

Keyboard: every control is a native button, checkbox, link or input. The dialog has `role="dialog"`, `aria-modal`, a label and a description. It keeps Tab inside (while the file viewer is open over it, the viewer takes focus and keeps Tab inside itself), closes on Escape, and returns focus to the button that opened it, or to the card itself when a successful confirm has removed that button. If the file viewer is open on top of the dialog, the first Escape closes the viewer and gives focus back to the link that opened it, and the second Escape closes the dialog. The cards re-render only when their content changes, and focus is put back on the same control after a re-render.

- **Fields the spec leaves open:** whether `pendingUpdate.file` is a bare file name or a path (the page handles both, assuming `knowledge/proposals/` for a bare name), and what `tasks[].action` holds for conversion tasks (see deviation 1).

Deviation on fix 13: the brief says the latest form is the last item of `inbox`. The running server lists `inbox` newest first (`projects.mjs` sorts by version, highest first; the real response had `2026-11-05-v2.md` before `2026-11-03-v1.10.md` and `2026-11-04-v1.md`), so the last item is the oldest. The card therefore picks the highest version in the file names (a repeat of one version ends `-2`, `-3`), which gives the right file for different versions whichever way the server orders the list. Two copies of the same version (a new project uploaded twice before its sheet exists) are told apart by the date in the file name, newest first, then by the `-2`/`-3` suffix (corrected in T-20261104-19; the first version took the older copy). The link text is "v<version>, <date>"; the full path is in the tooltip. Please tell the backend owner if the order is meant to change.
