## Problem

The review passed Projects at 83 but found one gap that should be closed before merging, and several smaller ones:

- **A.** A confirm named only the project, not the text the person had read. If an agent started editing the sheet while the dialog was open, Confirm still marked whatever was on disk as confirmed.
- **B.** After an in-place update upload, a `new` confirm recorded the uploaded form's version even if the sheet was never updated from it.
- **C.** The UI's "Latest form" picked the older copy when two copies had the same version.
- **D.** A confirmed-sheet update now has two files (the sheet and a review list), and the server had to follow the template.
- **E.** Agents could still write into `knowledge/proposals/applied/`.
- **G.** Two typos.

## Decisions I made, and one consequence for you to rule on

1. **Missing hash is a 400, not accepted.** The brief says only that a mismatch gives 409. I made a missing or malformed `sha256` a 400, because an old cached page would otherwise confirm with no check. Every confirm test that is not about the hash goes through a helper that adds the hash of the file on disk.
2. **B, as written, records `0` for a normal new project.** Converted sheets do not carry a frontmatter `version` (the template maps the form's version to `last_verified` and the Changes section, template line 51). So the first confirm of a freshly converted project now records `0`, and the list shows "v0" after it, where before it recorded and showed the form's version (`1`). A re-upload of v1 is still refused, because the inbox holds it. The existing test of a new confirm now expects `0`. The safe fix, if you want the version to show: have the CONVERT and UPDATE_IN_PLACE tasks tell the agent to write `version: <n>` into the sheet's frontmatter (r2 suggested this). I did not do it, because the brief didn't ask for it and it changes agent task wording and the agent's output.
3. **No attempt to guess the version from file dates.** I considered treating the form as the sheet's version when the sheet is newer than the form, but that is a guess; not done.

## Risks

- Item 2 above: "v0" on freshly confirmed projects until the version line is written by the agent.
- The 400 for a missing hash means a page opened before this change must be reloaded before it can confirm. The server restarts with the new code anyway; the message says "Reload the page".
- `control.mjs` still lists any file in `knowledge/proposals/` as "Proposal waiting for a person to apply and confirm", so a `-changes.md` file shows as its own item beside its sheet. It is only a list entry (the viewer reads it). Left alone; a later change could hide `-changes.md` there.
