## The change

A signed-in person can upload a filled `knowledge.md`, see every project, queue work on selected projects, and confirm a sheet.

- **Upload** validates the form, saves it unchanged under `knowledge/inbox/<slug>/<date>-v<version>.md` (`-2`, `-3` if the name is taken), and queues one Jarvis task. The task text is fixed wording plus the validated slug and file path. No form text goes into it.
- **New vs update.** No `knowledge/products/<slug>.md` means new (a convert task). A sheet means update (a compare task), and the version must beat the newest version on record for the slug (inbox file names, `ops/confirmations.jsonl`, a `version:` line in the sheet). A sheet with no record, such as MotionRepo's, counts as 0.
- **Work** queues one task per slug, fixed wording per action, at most 5 slugs. `leads`, `outreach` and `demo` need `status: confirmed`; `research` does not. Refusals come back per slug with a reason.
- **Confirm** needs `{kind, by, phrase}` with `phrase` equal to `confirm <slug>`. `new` sets `status: confirmed` and `last_verified`. `update` copies the current sheet to `knowledge/history/<slug>/`, writes the newest proposal over the sheet as confirmed, and moves the proposal to `knowledge/proposals/applied/`. Every confirm appends a line to `ops/confirmations.jsonl`. Nothing to confirm gives 409.
- **List** returns every `knowledge/products/*.md` except `_template.md`.
- **`kb.mjs status`** skips `knowledge/templates/`, `knowledge/inbox/`, `knowledge/history/` and `knowledge/proposals/applied/`.

## Routes, with examples

All JSON, errors are `{message}`. Every route needs the sign-in when it is on. Every POST needs the same-site header and Origin (`X-Team-Page: 1`, `Origin: http://127.0.0.1:<port>`).

```
GET /api/projects
200 [{slug, name, status, version, lastUpdated, stage, website, path,
      pendingUpdate: {file, version}|null,
      inbox: [{file, at}], history: [{file}], tasks: [{id, status, action}],
      canWork: {research: true, leads, outreach, demo}}]

POST /api/projects/upload   {"filename":"knowledge.md","content":"---\nname: Acme Tool\n...\nversion: 1\n---\n..."}
200 {slug:"acme-tool", kind:"new", version:"1", taskId:"J-20261104-01", file:"knowledge/inbox/acme-tool/2026-11-04-v1.md",
     message:"New project acme-tool, version 1. An agent is converting it to a fact sheet. Task J-20261104-01 is queued. It is starting."}
400 {message:"The frontmatter has no filled_by: write the name of the person who filled in the form."}
409 {message:"Version 3 is not newer than 3. Raise the version in the form and add a row to its change log, then upload again."}

POST /api/projects/work   {"slugs":["acme-tool","motionrepo"],"action":"leads"}
200 {queued:[{slug:"motionrepo", taskId:"J-..."}],
     refused:[{slug:"acme-tool", reason:"The fact sheet is proposed, and leads work needs a confirmed sheet. Confirm it first."}],
     message:"1 task queued, 1 refused. The first is starting."}
400 for more than 5 slugs, an empty list, or an action other than research, leads, outreach, demo

POST /api/projects/acme-tool/confirm   {"kind":"new","by":"Suryanshu","phrase":"confirm acme-tool"}
200 {slug:"acme-tool", status:"confirmed", message:"..."}
400 wrong phrase, missing or over-80-character name, bad kind    409 nothing to confirm
```

Notes for developer B and the coordinator, where the spec left room:

- `file` values (`inbox[].file`, `history[].file`, `pendingUpdate.file`) are repo-relative paths, so they go straight into `/api/file?path=`. `path` is the sheet's own path.
- `version` is always a string. It is the last confirmed version, else a `version:` line in the sheet, else the newest uploaded form, else `"0"` (MotionRepo shows `"0"`).
- `tasks[].action` is `convert`, `update`, `research`, `leads`, `outreach`, `demo` or `other`. A task is matched to a project by the slug in the fixed places the server's wording puts it (`product <slug>`, `inbox/<slug>`, `products/<slug>`), so a free-text task that merely mentions a slug is not matched. Newest first, at most 10.
- An unknown `/api/projects/...` path falls through to the existing 404.

## Risks

- A converted sheet that fails or is abandoned leaves its form in the inbox. For a **new** project, uploading the same version again is allowed (no sheet exists, so no version check); for an **update**, the failed version number is used up and the form needs a higher one.
- Two quick identical uploads of a new project queue two convert tasks. The UI should disable the button while a request is open; the server does not de-duplicate.
- `markConfirmed` is the old `kb.mjs confirm` code moved, unchanged in behaviour; `kb.mjs confirm` now runs through it.
- The upload size cap on the body (1 MB) is larger than the 300 KB form limit because JSON escaping grows the text; a signed-out or other route still stops at 16 KB.
- Update confirm trusts the proposal the agent wrote: it requires frontmatter and, if a `slug:` is there, that it matches. It does not check the proposal's own `status`. The reviewer who confirms is reading the file in the viewer, as the spec says.
- A project's `version` in the list for a sheet built from a form but never confirmed is the newest uploaded version, which is a hint, not a recorded fact.
