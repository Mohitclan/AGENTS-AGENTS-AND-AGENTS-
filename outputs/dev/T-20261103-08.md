## Definitions

**Reply rate.** Live outreach only. A send with `mode` other than `live` is never counted (demo sends are counted and reported as excluded).
- **Unit: a contact** (the lead ID, else the address). The 14-day window (`ops/approvals.md` condition D) runs from the first live send to that contact and is closed once 14 full days have passed. Only closed contacts are in n. Contacts still inside the window are reported as "still open", never as misses.
- **A reply** is a recorded `reply`, `opt_out` or `complaint` that arrived from the first live send up to 14 days after it (both ends inclusive). An auto-reply is not a reply. A reply after the window, and a reply dated before the first send, are reported separately and not counted.
- **`--since <date>`** keeps the contacts whose first live send is on or after the date. All live sends are grouped first, so a contact first emailed before the date is left out whole (and reported), not restarted at a later follow-up.
- **A contact whose email bounced** is left out of both sides and reported.
- The rate comes with a 95% Wilson interval (z = 1.959964).
- **Below the minimum**: prints `not enough data (n=X, need ≥10)` plus a tally ("0 of 0"), and no percentage or interval.

**Reviews.** The task and round come from the file name (`T-…-NN-r2.md`; the old `-review.md` names are round 1).
- **Revisions per task = number of reviews − 1.** The number of reviews is the larger of the file count and the highest round seen, because a file `-rN` proves rounds 1 to N took place. The average is over tasks, with n shown. A lettered sub-task name (`T-20261103-09a-r1.md`) is read as its own task.
- **First-review pass rate** = PASS results in each task's round 1 review over all results in those reviews. A review with a per-draft table (a header with a `Verdict` column) contributes one result per draft, and the Overall row is skipped, so a split verdict counts every draft. Without a table the frontmatter `verdict:` is used, then the first PASS, REVISE, ESCALATE or FAIL on the Verdict line ("above the PASS line" is ignored). A headline that names two different verdicts raises a "Check:" line. A table whose first column is a list of checks (Item, Check, Rule, Claim, Criterion, Probe, Fix, Source, Test, Call, Area, Mutant, Step) is not read as drafts, and when a table is used but its verdicts do not include the headline or frontmatter verdict, a "Check:" line says so (counts do not change).
- A task with no round 1 file (T-20261102-03 only has r2) is flagged and left out of the first-review rate. Its r2 file proves an r1 review happened, so its revisions are counted from the highest round: T-20261102-03 shows 1.

**Objection recovery rate.** The definition is the "Brief for P4" section of `outputs/sales/skill-drafts/README.md` (lines 57-69 as the file stands today), together with rows 3 and 4 of the Assumptions table in `outputs/reports/2026-11-03-gtm-adoption-shortlist.md`. (Round 1 took it from `objection-handling-addition.md`, which holds only a one-line pointer; that was the wrong file.) Of the objections whose answer a person sent, with 7 days passed since the answer, the share where the buyer wrote back inside those 7 days.
- Answers under 7 days old are "pending" and outside both sides.
- **Wrote back** (`OBJECTION_RECOVERED` in code): `interested`, `objection` (a second objection), `referral`, `wrong_person`, `not_now`. The set is fixed in code so it cannot drift. A reply after the wait, or dated before the answer was sent, is reported and not counted.
- **Moved forward** (`MOVED_FORWARD`): `interested` only for now (whether `referral` joins is the approver's call). It is reported as its own count beside the rate, with n, under the same minimum. `not_now` is wrote back but not moved forward, so a chain of "later" replies does not read as success.
- **In n but not wrote back:** `declined` (a flat no with no new reason), `opt_out`, `complaint`, `auto_reply`, and no reply at all.
- **Left out of both sides, and reported:** `bounce`, `unknown` (not labelled yet) and `needs_person` (held until a person labels it; `HELD_FOR_PERSON`).
- **Smokescreen share: built.** The log carries the two markers the objection-handling draft names, `pre_information` and `no_specifics` (`yes` or `no`; `unknown` or missing means not marked). Of the answers in n with both markers known, the share with both `yes`, under the same minimum and printing rule; answers without both markers are counted and left out of that share. The third marker, `immediate_drop`, is not counted by any command (the brief asks for no count of it).
- **Minimum:** default 10, not the source's 5 (assumption 3 in the shortlist). Below 10, counts only and no percentage. "Never change an answer because of a rate while n is below 15" is a rule for the reader and is written in the skill draft, not in the script.

**Row 14 (B14) levels and floors.** The 95% level and Wilson formula are the source's. The source's floors for segment analysis (100 contacted, 20 replies, 30 per cell) are not built: segment analysis is the later `outcome-analysis` skill. Every rate here uses the single minimum (default 10, `--min`).

## Objection data (no source exists yet)

`objections` prints "no objection data yet". The sales skill should write **`outputs/sales/objection-log.jsonl`**, appended only, one JSON object per line. Minimal format, all that the script reads:

```
{"id":"O-001","lead":"L-xxxxxxxx","answer_sent":"2026-11-10","reply_at":"2026-11-12","reply_category":"interested","pre_information":"no","no_specifics":"no"}
```

- `id`: one per objection. To update it, append a new line with the same `id`; the latest line wins and no line is deleted, so counts don't shift.
- `answer_sent`: the date a person sent our answer. `null` or missing means the answer was only drafted, and it is not counted.
- `pre_information`, `no_specifics` (optional): the two smokescreen markers, `yes` or `no`, written before the answer (`unknown` or missing means not marked). They feed the smokescreen share only.
- `reply_at`, `reply_category`: when and what the buyer wrote back. `reply_category` is one of: `interested`, `objection`, `referral`, `not_now`, `wrong_person`, `needs_person`, `declined` (a flat no that is not an opt-out), `opt_out`, `complaint`, `auto_reply`, `bounce`, `unknown`. These are the reply-triage categories in snake_case, plus `declined`. An unrecognised label is left out and listed in a "Check:" line.

The objection-handling draft says "until the script exists, write 'not enough data, no counting script yet'". When P5 is installed that line should change to "run `node scripts/stats.mjs objections`". That edit belongs to the sales draft, not to this branch.

## Risks

- **Review parsing is a heuristic.** Review files are free text. The parser reads a verdict table, then frontmatter, then the Verdict line. I checked 43 real files in round 1 (and 10 more by the reviewer) by reading the per-task table in `--list`, and it matches the files I opened (for example T-20261030-07 first review = ESCALATE + REVISE, T-20261103-05 = PASS + PASS + PASS + REVISE). A future review in a new layout is reported as "unknown" and a headline naming two verdicts raises a "Check:" line, but it could still be misread. Putting `verdict:` in frontmatter, as the evaluator now does in some files, avoids this.
- **Contact, not send, is the unit for reply-rate.** The brief says "a send counts once its window has closed". Email 2 and 3 only go out when there is no reply, so a per-send rate would count the same non-reply three times and understate the true rate. I used one row per contact with the window from the first send. If the human prefers per-send, it is a small change.
- **What counts as a reply** (reply, opt-out, complaint) and leaving bounces out are my calls. A person can reverse them in `RESPONDED` and the bounce rule.
- **The tool trusts the logs.** `ops/replies.jsonl` is written only by `replies.mjs`, which has not run against a real inbox here (not run, by instruction). The reply path is tested on fixtures only; its field names (`kind`, `mode`, `lead`, `sent_to`, `send_message_id`, `received`) were read from the code in `replies.mjs`, not from a real log line.
- **Time zones.** Windows are counted in UTC milliseconds from the send's ISO time, so "14 days" is exact; `--since` and `--as-of` dates are read as UTC midnight.
- **The agents must be told.** The script only helps if the guardrails skill and briefs say to use it (the draft addition does). A hook that rejects a typed percentage would be a separate job.
- **The numbers on real data are small.** Reply rate has n=0, so nothing can be said yet. The review figures have n=37 results and n=24 tasks and carry intervals.
