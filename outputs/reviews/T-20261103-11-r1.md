### 2. `suppress`: the core works, but `gmail.com` is accepted

- **What works.** `suppress` stores normalised profile URLs: `HTTPS://www.LinkedIn.com/in/Asha-A/?utm=x#top` is stored as `https://linkedin.com/in/asha-a`, and `https://mobile.twitter.com/Asha?s=20` as `https://x.com/asha`. It refuses `linkedin.com`, `https://www.linkedin.com/`, `x.com`, `github.com`, `github.io`, `www.github.io`, `substack.com`, `linkedin.com/in`, `https://linkedin.com/in/` and `linkedin.com/company`, each with exit 1 before any write.
- **`gmail.com`: not refused.** In the scratch copy, `suppress gmail.com "probe"` printed `Suppressed gmail.com.` (exit 0). The same holds for `googlemail.com`, `outlook.com`, `hotmail.com`, `yahoo.com`, `proton.me`, `icloud.com`.
- **Why it should be refused.** I found no reason against refusing it, and one more reason for it. Such an entry would also make `send-email.mjs` refuse the internal demo inbox `shivamkgjj2005@gmail.com` (main memory, 2026-11-02), because `isSuppressed` now goes through the same matcher. Fix 1.

### 3. Old bare shared-host entries: not safe enough

The current design: such an entry matches nothing, `check` warns on stderr, and the exit code stays 0. I judge this unsafe under hard rule 7, for three reasons:

- **Assumption 33 creates these entries.** Until this branch merges, coordinator assumption 33 says to record a LinkedIn or X opt-out "by URL plus hold" on `main`. `main`'s `suppress` turns that URL into the bare `linkedin.com`. So these legacy entries are what the team will create during the interim, not a theoretical leftover.
- **Each one is a real opt-out we can't tie to a person.** The hold protects that one lead. But once merged, the entry protects no one. If the same person is imported again (another product, a new lead ID), nothing stops it: `suppressionMatch` skips the entry in import, `set-status`, gate and `send-email`.
- **The only signal is a stderr line from `check`, with exit 0.** The `gate`, which is what people run before drafting, says nothing. In my probe, a legacy `linkedin.com` entry gave `OK: 8 lead(s), no problems found.` with exit 0, and the gate showed Cool Analytics (a LinkedIn contact) with no suppression reason.

Fix 2 makes it fail closed.

### 4. The two accepted calls

- **Import and `set-status` use the wider match: safe.** It only adds blocks, and it is what makes the gate and `set-status` agree. Its downside is that an over-broad entry now blocks everywhere, not only in the gate. That makes fixes 1, 5 and 6 more pressing, not less.
- **A profile URL covers pages below it on a `/` boundary: safe for person pages.** `asha` does not cover `asha-b` (tested and probed), and sub-pages such as `/details/experience` are covered, which is the reason for the choice. It is unsafe only where the stored "profile" is not one person:
  - a root or `/in` entry written by hand (fix 3)
  - a query-identified page (fix 6)
- Neither call has a dedicated test: the "exact URL only" mutant survived (fix 7).

## Required fixes

1. **Refuse free-mail domains in `suppress`.**
   - **Where:** `scripts/_shared.mjs`, `classifySuppression`.
   - **The list:** move `PERSONAL_MAIL` from `scripts/leads.mjs:59-62` into `_shared.mjs` so the gate's personal-mail signal and `suppress` read one list, then refuse a bare entry on it.
   - **The message:** something like `gmail.com is a personal mail service: suppressing it would cover every address there. Give the person's email address instead`.
   - **Tests:** `gmail.com`, `GMAIL.COM` and `https://gmail.com/` are refused, and `asha@gmail.com` is still accepted.
   - **Write-up:** update Risks ("Personal mail domains…") and human check 4.
2. **Make a legacy bare shared-host entry fail closed.**
   - **Where:** `scripts/leads.mjs:490-493` and `_shared.mjs` `suppressionMatch`.
   - **The check:** `check` must exit 1 while such an entry exists. The message names the entry and says: re-enter the person as a profile URL, then a person removes this line.
   - **The match:** until it is removed, the matcher should treat the entry as covering contacts on that host, with a distinct reason, e.g. `suppressed (legacy linkedin.com: re-enter as a profile URL)`. Then the gate, import, `set-status` and `send-email` all hold, not just one lead.
   - **Docs and tests:** update `pipeline/lead-schema.md` (last paragraph of Suppression) and the test at `lead-gates.test.mjs:385`.
   - **If the coordinator prefers no over-block:** the minimum is `check` exiting 1 plus the gate printing the warning.
3. **Have `check` validate every suppression entry, not only bare hosts.**
   - **The rule:** run each `value` through `classifySuppression`. A refused value, or one whose stored form differs from the canonical form, fails the check and prints the canonical form.
   - **Probed:** a hand-written `https://www.linkedin.com/` (or `linkedin.com/`, `https://linkedin.com/in`) Stops every LinkedIn lead with no warning. In the scratch copy, Cool Analytics showed `suppressed (https://www.linkedin.com/)` while `isBareSharedHostEntry` returned false.
   - **Also probed:** a hand-written `www.acme.com` matches nothing.
   - **Why it matters:** the schema says people edit this file by hand ("Removing an entry is a person's decision, made by editing the file"). Also canonicalise domain entries at match time (strip `www.`) so the second case is covered.
4. **Strip or refuse `mailto:`.**
   - **The bug:** `isEmail` (`_shared.mjs`, the `/^[^\s@/]+@…/` regex) accepts `mailto:asha@acme.com`. `suppress mailto:asha@acme.com` printed `Suppressed mailto:asha@acme.com.` and the entry covers no one. Likewise, an `asha@acme.com` entry does not cover a `mailto:asha@acme.com` contact.
   - **The fix:** strip a leading `mailto:` in `classifySuppression` and in `suppressionMatch`'s contact, or refuse it.
   - **Test:** add one.
5. **Don't let `canonicalHost` cut a company domain down to a TLD.**
   - **Where:** `_shared.mjs`, `canonicalHost`. Strip `m.`/`mobile.` only when the remainder is a shared host, and never reduce a host to a single label.
   - **Probed:** `suppress mobile.de` stored `de` (covers every `.de` lead), `m.me` stored `me`, `www.com` stored `com`.
   - **Test:** add one.
6. **Refuse shared-host URLs whose path is not one person.**
   - **The bug:**
     - `facebook.com/profile.php?id=123` is stored as `https://facebook.com/profile.php`, which covers every numeric-ID Facebook profile.
     - `youtube.com/watch?v=…` is stored as `https://youtube.com/watch`.
     - `x.com/i`, `x.com/home`, `youtube.com/c`, `youtube.com/channel` and `github.com/orgs` are accepted.
   - **The fix:** either keep the identifying query parameter (`id`) for `profile.php`, or refuse these paths with the same "does not name one person" message. `MIN_PATH_SEGMENTS` is the natural place for `youtube.com` `c`/`channel`/`user`.
   - **Priority:** this over-blocks rather than under-blocks, so it ranks below fixes 1-5. It is still the same "one opt-out stops other people" bug this task exists to fix.
7. **Pin the two accepted calls with tests.**
   - **Sub-pages:** assert that `https://linkedin.com/in/asha-a` covers `https://www.linkedin.com/in/asha-a/details/experience`. The "exact URL only" mutant survives today.
   - **Country sites:** assert that a contact on `in.linkedin.com` is covered. The mutant without the country-site collapse survives today.
