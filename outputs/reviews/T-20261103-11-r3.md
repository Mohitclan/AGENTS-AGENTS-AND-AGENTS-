## Brief item 2: the `@handle` gap, plainly

**It's small, it's real, and it doesn't block a PASS on its own.**

- **What happens.** On X, Instagram, GitHub, Facebook, Peerlist, linktr.ee and dev.to, `suppress https://x.com/@asha` stores `https://x.com/@asha`. That entry doesn't match a lead whose contact is `https://x.com/asha`, and the reverse fails too. `check` exits 0 on the entry, the gate keeps the lead Conditional, and `set-status <id> drafted` succeeds.
- **Real repro** (scratch copy with the real `leads.jsonl`):
  - `suppress "https://x.com/@_ojas_13"` prints `Suppressed https://x.com/@_ojas_13.` and then `No open lead matched; check the entry covers the person.`, exit 0.
  - SpaceWise stays Conditional, and `set-status L-64817c69 drafted` gives `Set 1 lead(s) to drafted.`
- **Why it doesn't block.**
  - The cue fires whenever the person is an open lead, and the developer's human check 2 tells the operator to read it.
  - X, Instagram, GitHub and Facebook are not allowed outreach channels, so the gate never gives those leads a Go.
  - The bare `@asha` is refused (`"@_ojas_13" is not a domain, an email address or a profile URL`, exit 1), so the commonest way to type a handle can't be stored wrongly.
- **Where it still bites.** The person isn't an open lead yet, and a later import (for any product) writes the other form. Nothing catches that today.
- **Other `@` shapes:**
  - `youtube.com/@`, `medium.com/@`, `producthunt.com/@` and `threads.net/@`: correct. On these hosts the `@` is part of the real URL, and it's kept on both sides.
  - The same miss occurs on `instagram.com/@asha`, `github.com/@asha`, `facebook.com/@asha`, `peerlist.io/@asha`, `linktr.ee/@asha` and `dev.to/@asha`.
  - `linkedin.com/in/@asha` misses too. LinkedIn public profile URLs don't contain `@`, so this one is low.
- **The exact fix.** I applied it to a scratch copy (`ev3fix`), never the worktree, and ran it.

  In `scripts/_shared.mjs`, above `QUERY_IDENTIFIED`:
  ```js
  // Hosts whose profile URL has no @, though people often type one: x.com/@asha is x.com/asha.
  const AT_DROPPED = new Set(['x.com', 'instagram.com', 'github.com', 'gitlab.com', 'facebook.com', 'peerlist.io', 'dev.to', 'linktr.ee',
    'calendly.com', 'bento.me', 'about.me', 'read.cv']);
  const dropAt = (host, path) => (AT_DROPPED.has(host) ? path.replace(/^\/@(?=[^/])/, '/') : path);
  ```
  In `normalizeProfileUrl` (line 205), `const path = dropAt(host, u.pathname.toLowerCase())...`. That covers both sides of the match and the stored value.
  In `readSuppression` (line 238), `const segs = dropAt(host, u.pathname.toLowerCase()).split('/').filter(Boolean);`. That way the profile is cut from the same path.

  Results with the fix applied:
  - All 10 `@` misses in my probe now match.
  - An entry already stored as `https://x.com/@asha` now matches `x.com/asha` with no re-entry.
  - YouTube, Medium, Product Hunt and Threads keep their `@`.
  - `lead-gates` + `send-email`: 74/74 with both the `@` fix and the email-wrapper fix (finding 2) applied in scratch.

  Add one test: `suppress https://x.com/@<handle>/status/1` disqualifies a lead whose contact is `https://x.com/<handle>`, and the reverse.
