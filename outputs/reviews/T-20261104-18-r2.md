## The UI's "latest form" rule, judged

Taking the highest version from the file name is the right primary key. It matches the server's own version rule, and it doesn't depend on list order. My probe (`r2/latest.mjs`, the real `pjLatestForm` against the real server list) shows it gets `v10` over `v2` and `v1.10` over `v1.9`.

The tie-break is wrong, though. `pjNewer` (`app.js:268-271`) ignores the date, and on equal `n` it takes the later item in the list. The server lists newest first, so the later item is the older copy:

| Inbox | Server order | UI "Latest form" |
|---|---|---|
| `11-04-v1`, re-upload `11-05-v1` | 11-05, 11-04 | **11-04** (older) |
| `11-04-v1`, `11-04-v1-2`, `11-05-v1` | 11-05, 11-04, 11-04-v1-2 | **11-04-v1-2** (older) |
| `v1`, `v1-2`, `v1-3` on one day | v1, v1-3, v1-2 | v1-3 (right) |

Headless Chrome agrees: `quote-tool`, with forms from 11-04 and 11-05 at v1, links "v1, 2026-11-04". Ties happen when a new project is uploaded again at the same version before its sheet exists. The server allows that, and the write-up discloses it. The server's own order is also wrong for same-day `-2`/`-3` copies (`localeCompare` puts `v1.md` first), though only the UI uses that order. The comment at `app.js:263` ("does not rely on the order … for a tie the last item") contradicts itself.
