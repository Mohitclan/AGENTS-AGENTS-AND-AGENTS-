# developer memory

What developer has learned. Claude Code loads the first 200 lines into every developer run.

- 2026-11-01 · When listing stale text left alone, search for the idea across customer surfaces, not the exact phrase in the changed files: a literal grep missed reworded copy that contradicted the fix. (source: outputs/reviews/T-20261101-01-r1.md · by: coordinator)
- 2026-11-01 · Say what each check covers, not only whether it ran, and test any 'stays true' claim against both flag settings before writing it. (source: outputs/reviews/T-20261101-01-r1.md · by: coordinator)
- 2026-11-02 · In a UI write-up, measure every number or behaviour you claim (text size, contrast, animation across refresh) in the browser before writing it, and label a figure worked out from formulas as calculated. Check hover and focus states for contrast as well as the resting state. (source: outputs/reviews/T-20261102-01-r2.md · by: coordinator)
- 2026-11-03 · Report a test run as it happened: give the suite's exit status and the pass/fail counts, never 'all pass' when one failed. If a failure looks unrelated, run the parent commit too and say it fails there as well. (source: outputs/reviews/T-20261103-03-r1.md · by: coordinator)
- 2026-11-03 · A guard test must also fail on a missing setting, not only a bad one: an agent file with no tools: line inherits every tool. (source: outputs/reviews/T-20261103-03-r1.md · by: coordinator)
- 2026-11-03 · When a brief points to a definition in another file (a README note, a decisions table), check your code against it line by line before marking 'one answer per question across files' as pass. (source: outputs/reviews/T-20261103-08-r1.md · by: coordinator)
- 2026-11-03 · Before coding a definition, open the brief the coordinator names and compare it label by label; do not mark 'one answer per question across files' pass from a file you did not open. Round 1 of T-20261103-08 took the objection labels from a file that held only a pointer, and the wrong labels passed my own self-review. (source: outputs/reviews/T-20261103-08-r1.md · by: developer)
- 2026-11-03 · When code normalises user input into a stored key (an opt-out, a domain, a URL), probe the odd inputs before calling it done: mailto:, country and multi-part suffixes, www., query-identified pages, bare roots and generic paths. Never store an entry that covers no one or everyone. (source: outputs/reviews/T-20261103-11-r1.md · by: coordinator)
- 2026-11-03 · Test a stored match key in both directions: what the user types in (a post, a message thread, a contact-info page) must still match the record it is meant to cover, not only the other way round. (source: outputs/reviews/T-20261103-11-r2.md · by: coordinator)
- 2026-11-05 · New skills: red-green-proof and root-cause-first. Before editing, check the tests can run (in this repo: node scripts/test.mjs, since plain node --test is refused); write a failing test first, prove the test catches the bug, and trace the bug to its origin before fixing. Stop after three failed fixes. (source: asked by the human on 2026-11-05; skills from the web research in outputs/research/2026-11-05-agent-skills.md · by: claude-code)
